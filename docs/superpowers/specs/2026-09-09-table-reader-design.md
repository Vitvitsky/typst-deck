# table_reader — проектная спецификация

Дата: 2026-09-09. Статус: **отложено в бэклог** (решение 2026-09-09).

Причина: продукт оформляет слайды, а не анализирует данные — от PowerPoint
аналитических действий не ждут. Спека сохранена целиком: описанная в ней
проблема (числа в графики печатает языковая модель) никуда не делась, и §1,
§3 и §6 остаются актуальными, если к вопросу вернутся.

## 1. Цель и границы

Числа в графиках сейчас печатает языковая модель. `extract.py` расплющивает
xlsx в markdown-таблицу, обрезает её на 200 строках и вставляет в промпт;
все инструменты в `llm/tools.py` принимают готовые литералы. Ни одной
проверяемой арифметической операции в конвейере нет — модель читает таблицу
глазами, считает в уме и печатает результат. Отсюда два дефекта: неверные
суммы и молча потерянные строки после двухсотой.

`table_reader` — отдельный пакет в этом же репозитории, который читает
табличные файлы и считает по ним агрегаты кодом. Он не знает ни про слайды,
ни про Typst, ни про LLM: на входе байты файла, на выходе профиль листов и
посчитанные ряды.

В первой версии:

- xlsx и csv; поддерживается только **чистая таблица** (§3), всё остальное
  отвергается с объясняющей ошибкой;
- один процесс, отдельного сервиса и HTTP API нет — граница проведена по
  API модуля;
- агрегаты: `sum`, `mean`, `min`, `max`, `count`, а также `none` (взять
  значения как есть);
- один уровень группировки.

Вне первой версии: поиск таблицы внутри произвольного корпоративного отчёта,
разъезд объединённых ячеек, многоуровневые шапки, сводные таблицы, несколько
уровней группировки, xls (старый формат), пересчёт графиков при изменении
исходного файла.

## 2. Ключевые принципы

1. **Числа в колоду пишет код, а не модель.** Инструмент агрегации сам
   кладёт результат в слайд. Модель выбирает *что* считать, но не имеет
   возможности напечатать значение руками.
2. **Молчаливая догадка запрещена.** Уверенности не хватило — отказ с
   объяснением или вопрос в чате. Промежуточного «наверное, имелось в виду
   вот это» нет.
3. **Требование про чистые таблицы живёт в валидаторе, а не в онбординге.**
   Объявленное, но не проверяемое правило хуже отсутствия правила: оно
   возвращает сегодняшнее тихо-неверное поведение и добавляет к нему
   основание сказать «мы предупреждали».
4. **Всегда отчитываться, что взято.** Лист, диапазон строк, колонки,
   исключённые строки — в каждом ответе, даже когда всё определилось
   однозначно. Это то, что делает числа проверяемыми.

## 3. Контракт: что такое «чистая таблица»

Лист проходит валидацию, если выполнено всё:

| # | Проверка | Код проблемы |
|---|---|---|
| 1 | нет объединённых ячеек | `merged_cells` |
| 2 | первая непустая строка — целиком непустые строки, они же имена колонок | `no_header` |
| 3 | между строками данных нет пустых строк-разделителей (хвостовые пустые строки отбрасываются молча) | `blank_row` |
| 4 | каждая колонка однородна по типу (число / текст / дата), с точностью до пустых | `mixed_column` |
| 5 | есть хотя бы одна строка данных и хотя бы одна числовая колонка | `empty_sheet`, `no_numeric_column` |

Проверка 4 — та, что ловит настоящую поломку: в смешанной колонке polars
типизирует всё строкой, и агрегировать становится нечего.

**Итоговые строки** — не ошибка, а отдельный случай. Их приносят и в
аккуратных выгрузках, и они дают худший отказ: сумма удваивается, а
результат выглядит правдоподобно. Правило: строка признаётся итоговой,
если её подпись совпадает с `^\s*(итого|всего|total|sum)` без учёта
регистра **и** её числовые значения равны сумме остальных строк. Совпало
и то и другое — строка исключается и это попадает в отчёт. Совпало только
одно — это неоднозначность, инструмент возвращает вопрос, а не догадку.

## 4. Пакет

```
src/table_reader/
  __init__.py     публичный API: profile(), aggregate()
  types.py        Sheet, Column, Problem, Aggregation, Provenance
  validate.py     пять проверок из §3, каждая возвращает Problem или None
  totals.py       распознавание итоговых строк
  aggregate.py    polars: group_by / агрегаты
  read.py         байты → сетка ячеек (openpyxl, csv)
tests/table_reader/
  corpus/         настоящие файлы (обезличенные) + синтетические
```

Публичный API:

```python
def profile(name: str, data: bytes) -> list[Sheet]:
    """Разбирает книгу. Не считает. Не бросает исключений на кривых листах —
    непрошедший лист приходит с ok=False и списком problems."""

def aggregate(name: str, data: bytes, *, sheet: str, label_column: str,
              value_column: str, agg: Agg = "sum",
              top_n: int | None = None) -> Aggregation:
    """Считает ряд для графика. Бросает TableError, если лист не прошёл
    валидацию или названные колонки не найдены."""
```

Типы:

```
Sheet:  name, ok, problems[], columns[], row_count, total_rows[]
Column: name, dtype ("number"|"text"|"date"), nulls, samples[]  # 3 значения
Problem: code, where ("A1:D1", «колонка "Q1"»), message  # готовый текст
Aggregation: data[{label, value}], used: Provenance
Agg: "sum" | "mean" | "min" | "max" | "count" | "none"
Provenance: sheet, rows ("3–57"), label_column, value_column, agg,
            excluded_rows[]  # с причиной
```

`read.py` читает xlsx через openpyxl с `read_only=False` — в
`read_only=True` объединённые ячейки недоступны в принципе, у
`ReadOnlyWorksheet` нет атрибута `merged_cells`, то есть нынешний путь
чтения структурно слеп к проверке 1. Цена — книга целиком в памяти;
ограничивается существующим `max_upload_mb`.

## 5. Интеграция с генератором слайдов

Меняются ровно две точки, остальной генератор не трогается.

**`extract.py`** — для xlsx и csv в промпт вместо 200 сырых строк уходит
профиль: листы, колонки с типами, число строк, по три примера значений на
колонку, найденные итоговые строки и — если лист не прошёл — список проблем
человеческим текстом. Обрезка `MAX_ROWS` перестаёт быть вопросом
корректности: числа больше не берутся из промпта.

**`llm/tools.py`** — новый инструмент:

```
chart_from_table(file, sheet, label_column, value_column,
                 agg="sum", top_n=null,
                 title, slide_id=null, after=null)
```

Инструмент считает ряд и **сам** создаёт или обновляет `bar-chart`-слайд.
Модели он возвращает текстовый отчёт: что посчитано и по каким строкам.
Значения через модель не проходят — это и есть принцип 1.

В колоду кладутся вычисленные литералы, а не запрос: колода остаётся
самодостаточным артефактом, каким она является сегодня, и не привязывается
навсегда к загруженному файлу. Провенанс попадает в реплику агента, а она сохраняется в `chat.jsonl`
через `store.append_chat` (`store.py:163`). Учесть: `DeckService.history`
(`service.py:56`) отбирает только сообщения с `role == "user"`, поэтому в
`/api/history` провенанс не виден — если он нужен и там, это отдельная
правка отбора.

Системный промпт получает правило: данные для графиков берутся только
через `chart_from_table`; печатать числа в `set_deck` и `update_slide`
запрещено, если источник — приложенный файл.

## 6. Ошибки и сообщения

Ошибка валидации — это текст для пользователя, а не код для разработчика.
Формат: что за файл и лист, какие именно ячейки, что сделать, и выход через
диалог.

> На листе «Отчёт» объединённые ячейки в A1:D1 и B2:C2, шапку колонок найти
> не смог. Пришлите лист, где первая строка — названия колонок, а дальше
> только данные. Или скажите, с какой строки начинается таблица.

Отчёт об успешном разборе идёт в ответ агента всегда:

> Взял лист «Продажи», строки 3–57, колонки «Категория» и «Выручка».
> Строку 44 «Итого» исключил из суммы.

## 7. Тестирование

- **Валидатор:** на каждый код проблемы из §3 — синтетический xlsx-фикстур
  и тест, что проблема найдена, названа правильными ячейками и не найдена
  на чистом аналоге.
- **Итоговые строки:** три случая — подпись и арифметика совпали
  (исключить), совпала только подпись (вопрос), совпала только арифметика
  (вопрос).
- **Агрегация:** golden-числа на фиксированной таблице для каждого агрегата.
- **Интеграция:** `FakeLLM` вызывает `chart_from_table`; проверяется, что
  `BarChartSlide.data` в колоде равен посчитанному, а не тому, что модель
  назвала в аргументах.
- **Доля прохождения:** отдельный прогон по корпусу настоящих отчётов,
  печатает процент листов, прошедших валидатор. Не тест, а измерение —
  см. §9.

## 8. Зависимости

Добавляется `polars`. `openpyxl` уже есть, но вызывается иначе
(`read_only=False`, §4). Ни браузера, ни второго тулчейна, ни второго
процесса проект не вводит. Кросс-проверка: разбор 5000×4 занимает 320 мс на
самом медленном варианте (openpyxl), полный рендер колоды — 182 мс, вызов
LLM — секунды. Скорость здесь не критерий выбора, и оптимизировать этот
слой не нужно.

## 9. Что проверить до реализации

**Доля прохождения на настоящих файлах.** Нужен корпус из 5–10 реальных
(обезличенных) отчётов и цифра: сколько листов проходит валидатор §3. Если
отвергается большинство, строгий контракт на практике означает
«инструментом не пользуются», и решение придётся пересматривать в сторону
мастера импорта с выбором диапазона — как это сделано в Power Query, где
разбор некрасивого листа — это цепочка явных шагов `Remove Top Rows` /
`Promote Headers` / `Fill Down`. Это дешёвая проверка, и она должна
предшествовать коду.

## 10. Риски и решения

- **Пользователь чистит таблицу руками и делает опечатку.** Требование
  чистого листа переносит ошибку из модели в человека, и такую ошибку не
  протестировать. Смягчение: отчёт из §6 показывает взятые строки и
  колонки, так что расхождение видно на глаз. Полное решение — мастер
  импорта, вне первой версии.
- **Модель обходит инструмент** и печатает числа в `set_deck`. Смягчение:
  правило в промпте плюс тест из §7. Жёсткая проверка (запрет литералов в
  графиках, когда к колоде приложен табличный файл) — если правило окажется
  недостаточным.
- **Книга целиком в памяти** из-за `read_only=False`. Ограничено
  `max_upload_mb`. Если упрёмся — читать диапазоны объединений напрямую из
  `xl/worksheets/sheetN.xml`, минуя openpyxl.
- **Корпус не наберётся.** Тогда доля прохождения неизвестна, и §9
  выполнить нечем. В этом случае первая версия выкатывается как есть, но
  отчёт из §6 становится обязательным к показу — он единственное, что
  делает ошибку заметной.
