# Ёмкость слотов шаблона — проектная спецификация

Дата: 2026-09-09. Статус: **принято к реализации**.

Первый из двух этапов. Второй — каталог вариантов слайдов, объявляемый шаблоном
(`agenda`, `two-column`, `dual-chart` и прочие, которые канон lmru-hr уже умеет,
а мы не показываем) — описывается отдельной спекой и опирается на понятие
объявленного слота, введённое здесь.

## 1. Цель и границы

Сейчас ёмкость текстовых полей — глобальные константы в `model.py`:
`TITLE_MAX = 120`, `BULLET_MAX = 200`, `bullets` до 6 на текстовом слайде и до 4
на слайдах с графиками. Они одинаковы для всех шаблонов, хотя шаблоны различаются
кратно: страница `default` — 453×255 pt, страница lmru-hr — 1919×1080 px, и у
второго в макете титульного слайда 180 мм жёстких отступов на 381 мм высоты.

Из-за этого модель пишет текст, который формально проходит валидацию, но не
помещается в вёрстку. 2026-09-09 это уронило четыре генерации подряд на боевой
колоде: пользователь просил отступы на титульном слайде, модель добавляла
переводы строк в `subtitle`, слайд переливался на вторую страницу и вся правка
откатывалась. Порог воспроизведён точно: три перевода строки собираются, четыре
уже нет.

**Задача:** дать шаблону объявить ёмкость своих слотов, довести эти пределы до
модели до генерации и проверять их при правке.

**В границы входит:**

- раздел `slots` в `template.json`;
- наложение объявленных пределов на схему, которую видит модель;
- проверка пределов в `ToolExecutor` с возвратом ошибки модели;
- автоподбор кегля в трёх шаблонах как страховка на границе;
- предупреждение при переезде колоды в более тесный шаблон.

**В границы не входит:**

- каталог типов слайдов (этап 2);
- пределы в миллиметрах: они всё равно упираются в метрики шрифта, а знаки и
  строки модель понимает лучше;
- динамические Pydantic-модели: `model.py` остаётся статическим источником истины.

## 2. Что установлено по коду

Проверено 2026-09-09.

- **Механизм уже есть, но глобальный.** `slide_schema()` (`model.py:111`) отдаёт
  JSON Schema, которую `build_system_prompt` (`llm/agent.py`) подставляет в
  промпт вместо `{{SCHEMA}}`. Модель уже видит `maxLength` и `maxItems` — просто
  одни и те же для всех шаблонов.
- **Цикл исправления уже есть.** `ToolExecutor.call` валидирует Pydantic'ом и
  возвращает модели строку, начинающуюся с `ERROR`; модель по ней исправляется.
  Это подтверждено тестами (`test_executor_set_template_unknown_ok_without_whitelist`).
  Новую механику вводить не нужно — достаточно добавить ещё одну проверку в тот
  же путь.
- **Автокегль уже есть в одном месте.** `template/deck.typ`, `heading-block`:
  заголовок измеряется через `measure()` и роняется с 19pt до 15pt, если не
  влезает в полторы строки.
- **Канон это предусматривает.** `templates/lmru-hr/slides_template.typ` объявляет
  `size-h1 = 64pt` и `size-h1-compact = 48pt`, а `content-slide` и `chart-slide`
  принимают `title-size` параметром.
- **Защита от переполнения есть только на содержательных слайдах.**
  `templates/lmru-hr/deck.typ:22` определяет `body-box` с `clip: true`, но
  `slide-title` и `slide-section` отдают управление канону напрямую. Поэтому
  переливается именно титульный слайд.
- **Проверка переполнения теперь называет виновника.** `render.py` определяет
  переполнившийся слайд по сдвигу страниц в `positions.json` и сообщает
  «слайд N «Заголовок» не помещается на страницу».

## 3. Формат объявления

`template.json` получает необязательный раздел `slots`. Первый уровень — тип
слайда (`title`, `section`, `image`, `bar-chart`, `chart`, `final`), второй —
имя поля этого типа.

```json
{
  "name": "Lemana Tech",
  "description": "Корпоративный шаблон Лемана Тех",
  "slots": {
    "title": {
      "title":      { "max": 60, "lines": 2 },
      "subtitle":   { "max": 90, "lines": 2 },
      "author":     { "max": 60, "lines": 1 },
      "department": { "max": 60, "lines": 1 }
    },
    "image": {
      "title":   { "max": 70, "lines": 2 },
      "bullets": { "count": 5, "max": 90 }
    },
    "chart": {
      "title":   { "max": 70, "lines": 2 },
      "bullets": { "count": 3, "max": 80 }
    }
  }
}
```

Три ключа, все необязательные:

| ключ | смысл | применим к |
|---|---|---|
| `max` | предельная длина значения в знаках | строковым полям и элементам списка |
| `lines` | предельное число строк | строковым полям |
| `count` | предельное число элементов | спискам (`bullets`, `labels`, `series`, `data`) |

### 3.1. Что именно означает `lines`

`lines` ограничивает **явные** строки: `value.count("\n") + 1 <= lines`.

Это сознательное сужение. Посчитать строки после автоматического переноса нельзя
без метрик шрифта и ширины блока, а тащить метрики в Python значит дублировать
работу typst и разъезжаться с ней. Зато явные переводы строки — ровно тот
механизм, которым модель ломала вёрстку 2026-09-09, и он проверяется точно.

Автоматический перенос закрывается двумя другими рубежами: автоподбором кегля
(§6) и проверкой переполнения при рендере (§2).

### 3.2. Потолок

Объявленные пределы могут только **сузить** глобальные из `model.py`, но не
расширить. Шаблон, объявивший `{"max": 300}` при `TITLE_MAX = 120`, получает
120: реестр шаблонов при чтении зажимает значение и пишет предупреждение в лог.

Причина — переносимость. Колода меняет шаблон (`POST /api/decks/{id}/template`),
и текст, написанный под расширенный предел, перестал бы проходить валидацию в
любом другом шаблоне.

## 4. Как пределы доходят до модели

`DeckService` строит схему для промпта, накладывая `slots` шаблона колоды на
результат `slide_schema()`:

- `max` → `maxLength` соответствующего свойства (или `items.maxLength` для списка);
- `count` → `maxItems`;
- `lines` → в `description` свойства добавляется фраза о числе строк, потому что
  выразить это средствами JSON Schema нельзя, а описание модель читает.

Схема, отданная модели, всегда согласована с проверкой из §5: обе строятся из
одного объявления.

## 5. Как пределы проверяются

Проверка добавляется в `ToolExecutor` сразу после Pydantic-валидации, в тот же
путь, что уже возвращает модели `ERROR`. Формат сообщения — как у существующих:
называется слайд, поле и нарушенный предел.

```
ERROR слайд 1, поле «Подзаголовок»: 4 строки при пределе 2 в шаблоне «Lemana Tech»
```

Ручные правки через API (`PATCH /api/decks/{id}/slides/{sid}`) проходят ту же
проверку и отвечают 422 с тем же текстом, чтобы поведение чата и панели свойств
не расходилось.

`ToolExecutor` создаётся в `run_agent`, который сейчас не знает о шаблоне колоды
ничего, кроме списка идентификаторов. Ему передаются объявленные пределы —
готовым словарём, а не объектом шаблона, чтобы слой LLM не зависел от реестра.

## 6. Автоподбор кегля

Страховка на границе: пределы приблизительны, и текст, уложившийся в 60 знаков,
всё равно может не влезть, если знаки широкие.

- `template/deck.typ` и `templates/dark/deck.typ`: приём из `heading-block`
  распространяется на `slide-title` и `slide-section`.
- `templates/lmru-hr/deck.typ`: используются `size-h1` и `size-h1-compact`,
  которые канон уже объявил; выбор — по результату `measure()`.

Автокегль не заменяет пределы. Без пределов модель пишет абзац в заголовок, и он
формально влезает кеглем 18pt, который не читается из зала.

## 7. Переезд в более тесный шаблон

`change_template` проверяет колоду против `slots` нового шаблона и возвращает
**предупреждение**, не отказ: список слайдов и полей, которые не проходят.
Предупреждения едут в существующее поле `warnings` ответа колоды и показываются
той же плашкой, что и предупреждения о пропавших картинках.

Блокировать нельзя: иначе колода застревает — её нельзя ни оставить в старом
шаблоне, если он закрыт, ни перенести.

Сборка после переезда либо сожмётся автокеглем, либо упрётся в проверку
переполнения, которая теперь называет конкретный слайд.

## 8. Обратная совместимость

- `template.json` без раздела `slots` — поведение ровно как сейчас, глобальные
  пределы. Так остаются `default` и `dark`, пока для них не подобраны значения.
- Колоды, созданные до этой правки, не мигрируют: пределы применяются при
  следующей правке. Уже сохранённый слишком длинный текст не ломает сборку — он
  либо сожмётся кеглем, либо даст понятную ошибку переполнения.
- Ручная правка, уменьшающая нарушение (например, текст был 200 знаков при
  пределе 60, стал 100), **проходит**: иначе колода, созданная до пределов,
  становится нередактируемой. Проверка отвергает только то, что нарушает предел
  и при этом стало хуже прежнего.

## 9. Тесты

- объявленные `max`, `lines`, `count` доезжают в схему, отданную модели;
- `ToolExecutor` отвергает превышение по каждому из трёх ключей и возвращает
  `ERROR` с именем слайда и поля;
- шаблон не может расширить глобальный потолок: `{"max": 300}` при
  `TITLE_MAX = 120` даёт 120;
- `lines` считает явные переводы строки: три перевода при пределе 2 отвергаются,
  один проходит;
- `template.json` без `slots` — поведение не изменилось;
- ручная правка через API отвечает 422 с тем же текстом;
- правка, уменьшающая существующее нарушение, проходит;
- длинный заголовок собирается во всех трёх шаблонах благодаря автокеглю;
- переезд в тесный шаблон даёт предупреждение и не блокируется;
- воспроизведение бага 2026-09-09: четыре перевода строки в подзаголовке
  титульного слайда lmru-hr отвергаются проверкой **до** рендера.

## 11. Риски

- **Значения пределов для lmru-hr придётся подбирать эмпирически.** В спеке они
  указаны как ориентир; настоящие получаются прогоном по вёрстке. Подбор — часть
  реализации, а не догадка: у нас есть воспроизводимый способ измерить порог
  (перебор длины до срабатывания проверки переполнения).
- **`lines` не покрывает автоматический перенос.** Это записано в §3.1 сознательно;
  рубеж закрывается автокеглем и проверкой переполнения. Если окажется, что
  переносы ломают вёрстку чаще явных строк, придётся возвращаться к измерению
  через `typst query` — тогда это отдельная задача.
- **Автокегль меняет вид уже существующих колод.** Заголовок, который сейчас
  обрезается или переливается, после правки станет мельче. Это улучшение, но
  визуально заметное; стоит предупредить пользователей перед выкаткой.
