# Делегированная личность и владение колодами — проектная спецификация

Дата: 2026-09-09. Статус: **принято к реализации**.

Реализует этап 1 плана `docs/superpowers/plans/2026-09-09-multiuser.md` и снимает
четыре его открытых вопроса: периметр корпоративный, личность — корпоративный
логин, доступ по ссылке нужен, существующие колоды достаются одному владельцу.

## 1. Цель и границы

Сервис задуман как агентное ядро: бот в корпоративном чате вызывает инструмент
генерации, получает PDF и ссылку на веб-версию, где презентацию можно доработать
руками или промптами. Ссылки расходятся по каналам. Человек заходит на веб и
видит, что он сам нагенерировал.

Сегодня это невозможно в принципе: понятия пользователя в сервисе нет. Колода,
созданная через `POST /api/agent/create_deck`, не принадлежит никому — нигде не
записано, кто попросил. Из этого следует и то, что «мои презентации» не
выражаются, и то, что любой правит и удаляет чужое.

**Ключевая мысль: бот — делегат, а не пользователь.** В каждом вызове от чата
участвуют две личности: сам бот (сервисный доступ) и человек, который попросил.
Сервис обязан записать вторую.

**В границы входит:**

- единая абстракция «кто спрашивает» с двумя источниками: заголовок от прокси и
  сервисный ключ с `on_behalf_of`;
- поля `owner` и `share_token` у колоды;
- проверка доступа на всех ручках колоды и задач;
- фильтрация списка колод и истории обращений;
- режим совместимости, при котором текущее развёртывание продолжает работать до
  появления корпоративного SSO;
- затирание заголовка личности в nginx.

**В границы не входит:**

- раздел «Открывал по ссылке» — см. §10;
- вынос состояния из процесса, квоты, индекс — этапы 2–4 плана;
- сам корпоративный SSO: сервис принимает заголовок, но не участвует в
  аутентификации.

## 2. Что установлено по коду

Проверено 2026-09-09.

- Модели пользователя, сессий, поля владельца и проверок прав в `src/typst_deck`
  нет ни одной.
- Агентское API (`api/agent.py`) — три ручки: `POST /api/agent/create_deck`,
  `POST /api/agent/revise_deck`, `GET /api/agent/decks/{deck_id}`. Синхронные,
  ждут задачу до `wait_seconds`, возвращают `outline`, `reply`, `pdf_url`,
  `edit_url`. Форма подходит инструменту чата; не хватает только личности.
- Бот и люди ходят одним путём `/deck/` за общим Basic Auth: отдельной точки
  входа для агента в nginx нет.
- Ручек колоды, требующих проверки, — семнадцать (`api/decks.py`), плюс
  `GET /api/jobs/{job_id}` и `GET /api/history`.
- `GET /api/jobs/{job_id}` возвращает `deck_id` и статус, то есть перебором
  идентификаторов задач можно узнать о чужих колодах. Ручку надо закрывать
  наравне с колодами.

## 3. Модель доступа

Три уровня. Разделены две ортогональные вещи, которые сейчас смешаны в
`deck_id`: **авторство** (кто сделал) и **доступ** (кто может открыть).

| уровень | кто | что можно |
|---|---|---|
| владелец | `deck.owner == caller.user` | всё: чтение, правка, удаление, история версий, чат |
| держатель ссылки | предъявил верный `share_token` | чтение слайдов, позиций, версий, скачивание PDF |
| прочие | — | ничего: **404** |

**404, а не 403.** Иначе по коду ответа перечисляются чужие колоды: 403 означает
«такая есть, но не твоя».

**Чат закрыт даже от держателя ссылки.** В нём лежат промпты и упоминания
загруженных материалов, то есть то, над чем человек работает. Ссылка даёт
посмотреть презентацию, а не переписку с моделью.

## 4. Откуда берётся личность

Новый модуль `src/typst_deck/identity.py`. Всё остальное опирается только на
него и не знает, откуда взялся логин.

```python
@dataclass(frozen=True)
class Caller:
    user: str        # корпоративный логин; "" — аноним
    via_bot: bool    # запрос пришёл через агентское API от имени пользователя
```

Зависимость FastAPI разрешает вызывающего по порядку:

1. **Сервисный ключ.** Заголовок `X-Service-Key` совпадает с
   `TYPST_DECK_SERVICE_KEY` → берём логин из поля `on_behalf_of` тела запроса →
   `Caller(user=<логин>, via_bot=True)`. Пустой или отсутствующий `on_behalf_of`
   при заданном ключе — ошибка 422: бот обязан назвать, за кого работает.
2. **Заголовок от прокси.** Имя настраивается (`TYPST_DECK_USER_HEADER`, по
   умолчанию `X-Forwarded-User`) → `Caller(user=<значение>, via_bot=False)`.
3. **Запасной пользователь.** Если ничего нет и задан `TYPST_DECK_DEFAULT_USER`
   → `Caller(user=<он>, via_bot=False)`. См. §8.
4. Иначе — `Caller(user="", via_bot=False)`, аноним.

Порядок важен: сервисный ключ старше заголовка, иначе бот, ходящий через тот же
прокси, получил бы личность прокси вместо личности человека.

### 4.1. Настройки

| переменная | по умолчанию | смысл |
|---|---|---|
| `TYPST_DECK_USER_HEADER` | `X-Forwarded-User` | имя доверенного заголовка |
| `TYPST_DECK_SERVICE_KEY` | пусто | ключ бота; пусто — агентское API работает как сегодня, при старте пишется предупреждение |
| `TYPST_DECK_DEFAULT_USER` | пусто | кем считать запрос без личности; пусто — строгий режим |

## 5. Изменения в модели колоды

```python
class Deck(_Strict):
    ...
    owner: str = ""
    share_token: str = Field(default_factory=lambda: secrets.token_urlsafe(16))
```

`owner` проставляется при создании из `Caller.user`. `share_token` генерируется
всегда, отдельно от `deck_id`: идентификатор попадает в логи, в ответ агентского
API и в тело сообщения в чате, и не должен давать доступ сам по себе. Раздельность
позволяет отозвать ссылку перегенерацией токена, не трогая колоду.

Колоды, сохранённые до этой правки, читаются без ошибок: оба поля имеют значения
по умолчанию, `share_token` дозаполнится при первом сохранении.

### 5.1. Ссылка

Формат: `/d/{deck_id}?s={share_token}`.

Существующие ссылки без токена продолжают работать для владельца — его пускает
собственная личность.

В ответе колоды и агентского API появляется `share_url` с токеном. `edit_url`
остаётся без токена и предназначен владельцу.

**Бот кладёт в чат `share_url`.** Это делает один линк пригодным для обоих
случаев: автор, кликнув его, получает полный доступ по своей личности — токен
ему не мешает; остальные в канале получают чтение.

## 6. Проверка доступа по ручкам

Один helper на все ручки: `require_deck(deck_id, caller, token, write=False)`.
Возвращает колоду либо поднимает 404.

**Только владелец** (`write=True`): `PATCH /api/decks/{id}`,
`POST …/template`, `DELETE /api/decks/{id}`, `POST …/uploads`,
`PATCH …/slides/{sid}`, `POST …/slides`, `DELETE …/slides/{sid}`,
`POST …/slides/{sid}/move`, `POST …/assets`, `POST …/revert`,
`POST …/messages`.

**Только владелец, хотя это чтение:** `GET …/chat` (§3).

**Владелец или держатель ссылки:** `GET /api/decks/{id}`,
`GET …/slides/{n}.svg`, `GET …/deck.pdf`, `GET …/positions`, `GET …/versions`.

**Особые:**

- `POST /api/decks` — создаёт колоду с `owner = caller.user`;
- `GET /api/decks` — только колоды вызывающего;
- `GET /api/history` — только его обращения;
- `GET /api/jobs/{job_id}` — доступ проверяется по колоде задачи; чужая задача
  отвечает 404;
- `POST /api/uploads` — промежуточная загрузка, колоды ещё нет; остаётся как
  есть.

Страница `/d/{deck_id}` продолжает отдавать статический HTML без проверки:
данные подтягиваются вызовами API, которые проверены.

`share_token` включается в ответ только владельцу — держателю ссылки он и так
известен, а лишний раз раздавать его незачем.

## 7. Агентское API

`CreateIn` и `ReviseIn` получают поле `on_behalf_of: str = ""`. При заданном
`TYPST_DECK_SERVICE_KEY` поле обязательно.

`GET /api/agent/decks/{deck_id}` проверяет доступ так же, как веб-ручки.

`agent_response` дополняется `share_url`.

Логин, который присылает бот, сервис принимает как есть: сопоставление
идентификаторов чата и корпоративных логинов — забота бота, не наша.

## 8. Как не сломать текущее развёртывание

Корпоративного SSO перед сервисом сейчас нет. Если включить фильтрацию по
владельцу как есть, все запросы станут анонимными, и владелец потеряет доступ к
своим четырём колодам.

Поэтому `TYPST_DECK_DEFAULT_USER`:

- **задана** — запрос без личности считается запросом этого пользователя.
  Сервис ведёт себя как сегодня: один человек видит всё. Колоды без `owner`
  тоже считаются принадлежащими ему, поэтому миграция данных не нужна;
- **пуста** — строгий режим для боевого контура с SSO.

Переключение — одна переменная окружения, обратимо.

## 9. nginx

Пока перед сервисом нет SSO, `X-Forwarded-User` можно прислать снаружи и стать
кем угодно. В `location /deck/` добавляется:

```nginx
proxy_set_header X-Forwarded-User "";
```

Когда появится SSO, строка меняется на передачу аутентифицированного
пользователя. **Без неё вся конструкция бессмысленна:** личность подделывается
одним заголовком.

## 10. Что откладываем

Раздел «Открывал по ссылке» в веб-интерфейсе. Чтобы он работал, надо помнить,
кто какую чужую колоду открывал, — это персональный индекс и запись при каждом
чтении. Такого состояния сейчас нет, и его место — этап 4 плана, где появляется
БД. Ссылки работают, но не запоминаются: человек хранит их в своём чате.

## 11. Тесты

- личность из заголовка; имя заголовка берётся из настройки;
- личность из сервисного ключа плюс `on_behalf_of`;
- сервисный ключ старше заголовка;
- заданный ключ без `on_behalf_of` — 422;
- неверный ключ — личность не выдаётся;
- запасной пользователь применяется, только когда нет ни ключа, ни заголовка;
- владелец проставляется при создании и из веба, и от бота;
- чужая колода отвечает 404 на каждой из семнадцати ручек;
- валидный токен даёт чтение слайдов, позиций, версий и PDF;
- валидный токен **не** даёт правку и **не** даёт чат;
- список колод и история содержат только своё;
- чужая задача отвечает 404;
- `share_url` есть в ответе колоды и агентского API;
- колода, сохранённая без `owner` и `share_token`, читается и дозаполняется;
- с заданным `TYPST_DECK_DEFAULT_USER` поведение совпадает с текущим.

## 13. Риски

- **Доверие к заголовку.** Строка из §9 — единственное, что отделяет модель
  доступа от подделки. Её отсутствие не проявится ни одним тестом приложения и
  не сломает ни одного сценария: всё будет работать и при этом ничего не
  защищать. Проверять при каждом изменении конфигурации nginx.
- **Логин как строка без проверки.** Сервис принимает то, что прислал бот или
  прокси. Опечатка в логине создаёт колоду, которую владелец не увидит. Лечится
  только на стороне источника личности.
- **Отзыв ссылки не реализован.** Токен генерируется один раз при создании;
  ручки перегенерации нет. Добавляется тривиально, но в границы не входит —
  вносить, когда появится запрос.
- **`TYPST_DECK_DEFAULT_USER` в боевом контуре.** Если её забыть снять после
  подключения SSO, любой запрос без заголовка станет запросом этого
  пользователя. Стоит логировать её значение при старте.
